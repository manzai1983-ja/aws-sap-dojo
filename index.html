CHAPTER 0

試験の全体像と解き方

Pro試験は「知っているか」より「要件に対して最適な1つを選べるか」を問う。

Associateとの違い

  • 問題文が長い：1問300〜500字の業務シナリオ。要件（制約）を拾う読解力が得点を左右する。
  • 選択肢がどれも「動く」：誤答も技術的には成立する。差は「運用負荷」「コスト」「最小の変更」「要件の網羅」。
  • 組織規模：数十〜数百アカウント、ハイブリッド接続、複数リージョンDRが前提。

問題文のキーワードと選ぶべき方向性

キーワード選ぶべき方向性
運用上のオーバーヘッドが最小 / LEAST operational overheadマネージド・サーバーレス・ネイティブ機能。自作Lambdaやスクリプトより既存サービス機能
最もコスト効率が高い / MOST cost-effective要件を満たす最小構成。DRならバックアップ&復元 → パイロットライト → ウォームスタンバイの順に安い
変更を最小限に / minimal changesリホスト・リプラットフォーム。コード改修（リファクタ）は避ける
今後作成されるアカウントにもOrganizations / Control Tower / StackSets（サービスマネージド・自動デプロイ）
RPO数秒・RTO数分Aurora Global Database、DynamoDB グローバルテーブル、Elastic Disaster Recovery
一元的に / centrally委任管理者アカウント、組織の証跡、Config アグリゲーター、Security Hub

解き方の型

  1. 最後の一文（何を求めているか：コスト？運用？可用性？）を先に読む。
  2. 本文から数値要件（RPO/RTO、帯域、期限、データ量）と禁止条件（インターネット経由不可、コード変更不可など）に印をつける。
  3. 禁止条件に反する選択肢を消す → 残りを「運用負荷・コスト」で比較。
  4. 迷ったらフラグを付けて先へ。180分で75問、1周目は1問2分目安、残り30分で見直し。
試験のツボ
  • 複数選択問題は「全部正解」で初めて得点。部分点なし。
  • 未回答は不正解扱い、誤答の減点なし → 必ず全問マークする。
  • 採点は補正型（compensatory）。ドメインごとの足切りはない。
TASK 1.1

組織の複雑さに対応するネットワーク接続戦略

多数のVPC・アカウント・オンプレミスをどう繋ぐか。Pro試験で最も出題が厚い分野の1つ。

この章の考え方
会社が大きくなると、VPCもアカウントも増え、オンプレミスともつなぐ必要が出てくる。場当たり的につなぐと配線が絡まり、1つの変更が全体に波及する。「ハブを1つ決めて集約する」「つなぐ範囲を必要最小限にする」の2つが設計の軸になる。
場面で理解する

Transit Gateway

場面
事業部ごとにアカウントを分けた結果、VPCが50を超えた。全VPCとオンプレミスを相互につなぎたい。
困りごと
ピアリングだと、VPCを1つ追加するたびに既存の全VPCとの接続とルート追加が必要になる。
解決
TGWをハブにして、各VPCはTGWに1本つなぐだけにする。
メリット
VPCが増えても作業量は1本分。ルートテーブルで本番と開発を分離でき、オンプレミスとの接続も1か所に集約できる。
注意
アタッチメントの時間料金とデータ処理料金がかかる。VPCが少なく通信量が多いならピアリングの方が安い。

VPCピアリング

場面
分析用VPCとDB用VPCの2つの間で、毎日大量のデータをやりとりする。
困りごと
TGWを経由すると、通信量に比例して処理料金が積み上がる。
解決
2つのVPCを直接ピアリングする。
メリット
時間料金がかからず、同じAZ内の転送は無料。経路も最短になる。
注意
推移的ルーティング不可、CIDR重複不可。3つ以上になったら管理が急に大変になる。

PrivateLink

場面
自社のAPIを他社や他部署に提供したいが、相手のネットワーク全体とはつなぎたくない。
困りごと
ピアリングやTGWだとVPC全体の経路が通じてしまう。相手とCIDRが重なっていると接続すらできない。
解決
NLBの背後のサービスをエンドポイントサービスとして公開し、相手はインターフェイスエンドポイントを作る。
メリット
公開範囲がサービス1つに限られる。CIDRが重なっていても使え、相手からは自分のVPC内のIPに見える。
注意
通信は一方向のみ。NLB（またはGWLB）が必要で、エンドポイントの時間料金がかかる。

Direct Connect

場面
基幹システムがオンプレミスに残っていて、毎日数TBのデータ連携がある。遅延も安定させたい。
困りごと
インターネットVPNは帯域と遅延が回線状況に左右される（1トンネルあたり最大約1.25Gbps）。
解決
データセンターとAWSを専用線（DX）で接続する。
メリット
帯域と遅延が安定する。AWSから外へのデータ転送料金もインターネット経由より安い。
注意
開通まで数週間〜数か月かかる。単体では暗号化されない。冗長化の度合いは費用しだい。

Site-to-Site VPN

場面
新しい営業所をすぐAWSにつなぎたい。またはDXが切れたときの予備回線が欲しい。
困りごと
DXは開通が遅く、費用も高い。
解決
インターネット上にIPsecトンネルを張る。
メリット
数時間で構築でき、安価で最初から暗号化されている。DXのバックアップとして定番。
注意
品質はインターネットしだい。大容量の常時通信には向かない。

Route 53 Resolver エンドポイント

場面
移行期間中、オンプレミスのアプリがAWS上のDBをホスト名で呼び、AWS上のアプリも社内のファイルサーバーを名前で引く。
困りごと
オンプレミスとAWSのDNSが、互いのドメインを知らない。
解決
インバウンドとアウトバウンドのエンドポイントを置き、転送ルールをRAMで全アカウントに共有する。
メリット
EC2上にDNSサーバーを立てて運用する必要がない。新しいVPCも、ルールを関連付けるだけで名前解決できる。
注意
エンドポイントはENI単位で時間料金がかかる。2つのAZに置いて冗長化する。

集中型インスペクション

場面
セキュリティ部門から「全通信を必ずファイアウォールで検査すること」と求められた。
困りごと
VPCごとにファイアウォールを置くと、台数もルール管理も爆発的に増える。
解決
検査VPCにNetwork Firewall（またはGWLB＋アプライアンス）を置き、TGWで全通信を経由させる。
メリット
ルールを1か所で管理でき、監査にも対応しやすい。
注意
全通信が1か所を通るため、遅延と処理料金が増える。アプライアンスモードを設定し忘れると通信がドロップされる。
仕組みと要点

VPC間接続の選択

方式特徴選ぶ場面
VPCピアリング1対1、推移的ルーティング不可、CIDR重複不可。データ転送は安価少数VPC間の単純な接続

ハイブリッド接続：Direct Connect (DX)

  • VIFの種類：プライベートVIF（VGW/DXGWへ）、パブリックVIF（S3などパブリックエンドポイントへ）、トランジットVIF（DXGW経由でTGWへ）。
  • Direct Connect Gateway：1本のDXから複数リージョンのVPC/TGWへ接続できるグローバルリソース。
  • 回復性モデル：最大回復性＝2つの別々のDXロケーションにそれぞれ2接続（計4本）。高回復性＝2ロケーションに1本ずつ。開発用＝1ロケーション2本。
  • 暗号化：DXは既定で暗号化されない。IPsecが必要ならDX上でSite-to-Site VPN（パブリックVIF経由、またはTGWのプライベートIP VPN）。専用接続10/100GbpsならMACsecも可（ホスト型接続は不可）。
  • バックアップ：DX障害時の低コストな代替としてSite-to-Site VPN（BGPでDXを優先）。

ユースケース
国内製造業A社（AWSアカウント40・VPC約60・工場12拠点）
  • IP設計：VPC IPAMで 10.0.0.0/8 を「東京 10.0.0.0/12」「大阪 10.16.0.0/12」に分け、各VPCへ /16 を自動で払い出す。工場のネットワーク（172.16.0.0/12）とは重ならないようにする。
  • 回線：2つのDXロケーションに1本ずつ（高回復性モデル）。VPNをバックアップにする。
  • 共有：ネットワークアカウントがTGWを所有し、RAMで組織全体に共有する。各アカウントはアタッチメントを作るだけでよい。
  • 例外：買収した子会社のVPCはCIDRが 10.1.0.0/16 で重複しているため、TGWにはつながない。必要なAPIだけPrivateLinkで公開する（図1-2）。

ハイブリッドDNS：Route 53 Resolver

  • インバウンドエンドポイント：オンプレのDNSからAWSのプライベートホストゾーンを引く（オンプレ側で条件付きフォワーダー設定）。
  • アウトバウンドエンドポイント＋転送ルール：VPCからオンプレのドメインを引く。ルールはRAMで他アカウントのVPCへ共有。
  • プライベートホストゾーンを他アカウントのVPCへ関連付けるには、CLI/APIで関連付け承認→関連付け。

集中型インスペクション・出口制御

  • インスペクションVPC（AWS Network Firewall またはGWLB＋サードパーティ製アプライアンス）をTGWに接続し、全VPCの東西・南北トラフィックを経由させる。
  • TGWのアプライアンスモードをインスペクションVPCのアタッチメントで有効化 → 往復で同じAZのアプライアンスを通り、非対称ルーティングによるドロップを防ぐ。
  • 集中型Egress：NAT GatewayをEgress VPCに集約してコスト・管理を一元化。
試験のツボ
  • 「CIDRが重複している顧客/部門にサービスを提供」→ PrivateLink。
  • 「推移的に」「数百のVPC」→ TGW。ピアリングはメッシュ管理が破綻する。
  • 「DXを暗号化」→ VPN over DX（MACsecは専用接続のみ）。
  • 「新しいVPCも自動的にオンプレ名前解決」→ Resolverルールを RAM で組織共有。
TASK 1.2

組織全体のセキュリティ統制

「誰が・どのアカウントで・何をできるか」をスケールさせて統制する。

この章の考え方
アカウントが増えると、「全員が正しく設定してくれる」という前提は崩れる。個々の設定に頼らず、組織として「これ以上はできない」という枠をはめ、違反は自動で見つけるのがProレベルのセキュリティ設計。
場面で理解する

SCP

場面
開発チームに自分たちのアカウントの管理者権限を渡したい。ただし、ログの停止や未承認リージョンの利用はさせたくない。
困りごと
IAMの設定をアカウントごとに見て回るのは不可能。管理者権限なら自分で制限を外せてしまう。
解決
OUにSCPをアタッチして、禁止操作をDenyする。
メリット
アカウント内の管理者でも超えられない上限になる。新しいアカウントもOUに入れた瞬間から適用される。
注意
SCPは権限を与えない（上限を決めるだけ）。管理アカウントには効かない。強すぎると業務が止まるので、検証用OUで試してから適用する。

アクセス許可の境界

場面
開発者がLambda用のロールを自分で作れるようにして、毎回の申請待ちをなくしたい。
困りごと
ロールを作れる＝自分より強いロールを作って権限昇格できてしまう。
解決
「指定の境界ポリシーを付けたロールのみ作成可」という条件付きの権限を与える。
メリット
作業の委任と統制を両立できる。インフラ担当がボトルネックにならない。
注意
境界ポリシー自体の変更・削除を必ず拒否しておく。

IAM Identity Center

場面
社員500人が20のアカウントにアクセスする。
困りごと
アカウントごとにIAMユーザーを作ると、退職者の削除漏れやパスワード・アクセスキーの管理が破綻する。
解決
既存のIdP（Entra ID、Oktaなど）と連携してシングルサインオンし、アクセス許可セットで権限を割り当てる。
メリット
入社・退社の処理はIdP側だけで完結する。使うのは一時的な認証情報のみになる。
注意
緊急時用に、IdPに依存しない手段（ブレークグラス用のアカウント）を別途用意する。

外部ID付きのクロスアカウントロール

場面
SaaSベンダーに、自社アカウントの読み取りを許可したい。
困りごと
ベンダーの別の顧客が、ベンダーを踏み台にしてこちらのロールを引き受けられてしまう（混乱した代理問題）。
解決
信頼ポリシーに、ベンダーが顧客ごとに発行する外部IDの条件を付ける。
メリット
正しい顧客としてのリクエストだけがロールを引き受けられる。長期キーを渡す必要もない。
注意
外部IDは秘密情報ではなく識別子。ベンダー側が顧客ごとに一意の値を発行する仕組みが前提。

委任管理者と組織への一括展開

場面
セキュリティ担当2人で100アカウントの脅威を監視する。
困りごと
アカウントごとにGuardDutyを有効化して見て回るのは不可能。新しいアカウントで有効化が漏れる。
解決
セキュリティアカウントをGuardDuty・Security Hubの委任管理者にし、自動有効化を設定する。
メリット
全アカウントの検出結果が1画面に集まり、優先度の判断ができる。新しいアカウントも漏れない。
注意
管理アカウントは委任するだけにし、管理アカウント上では日常の運用をしない。

組織の証跡＋Object Lock

場面
不正の調査や監査で、「ログが改ざんされていない」ことを証明する必要がある。
困りごと
攻撃者が管理者権限を奪うと、まず証跡を止めてログを消そうとする。
解決
組織の証跡をログアーカイブアカウントのS3に出力し、Object Lock（コンプライアンスモード）をかける。
メリット
本番アカウントが乗っ取られても、ログは誰も消せない。
注意
保持期間中は本当に削除できないので、保存期間とコストを見積もってから設定する。
仕組みと要点

権限の評価順と各ポリシーの役割

ポリシー役割注意点
SCP（サービスコントロールポリシー）OU/アカウントの権限の上限を設定。権限は付与しない管理アカウントには効かない。サービスリンクロールにも効かない
RCP（リソースコントロールポリシー）組織内リソース（S3、KMS、SQS等）へのアクセス上限組織外プリンシパルからのアクセス制限に有効
アクセス許可の境界IAMユーザー/ロールの権限上限開発者にロール作成を委任する際の権限昇格防止
リソースベースポリシーS3・KMS・SQSなど側で許可aws:PrincipalOrgID で組織内のみ許可
セッションポリシーAssumeRole時に一時的に絞る—

明示的なDenyは常に優先。有効な権限＝SCP ∩ 境界 ∩ アイデンティティポリシー（∪ リソースポリシー）。

}
② 組織内だけに公開するS3バケットポリシー：アカウントIDを列挙しないので、アカウントが増減しても書き換える必要がない。 
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::shared-master-data/*",
  "Condition": { "StringEquals": { "aws:PrincipalOrgID": "o-a1b2c3d4e5" } }
}
③ 権限委任の型：開発者には「iam:CreateRole は iam:PermissionsBoundary が DevBoundary の場合のみ許可」という権限を与え、境界ポリシー自体の変更（iam:DeletePolicy 等）は拒否する。

アイデンティティ

  • IAM Identity Center：外部IdP（Entra ID、Okta等）とSAML/SCIM連携し、アクセス許可セットで複数アカウントへSSO。Pro試験の「推奨」解。
  • クロスアカウントロール：第三者に委任する場合は外部ID（ExternalId）で「混乱した代理」問題を防ぐ。

検出・監査サービスの組織展開

  • GuardDuty / Security Hub / Macie / Inspector / Detective：セキュリティアカウントを委任管理者に指定し、新規アカウントを自動有効化。
  • CloudTrail 組織の証跡：全アカウントのAPIログをログアーカイブアカウントのS3へ。S3 Object Lock（コンプライアンスモード）で改ざん防止。
  • AWS Config アグリゲーター：組織全体のコンプライアンスを集約。適合パックで標準ルールを一括展開。

暗号化とシークレット

  • KMS：キーポリシーが一次の制御。クロスアカウント利用はキーポリシー＋相手側IAMの両方で許可。マルチリージョンキーでリージョン間の再暗号化を回避。
  • Secrets Manager：自動ローテーション（RDSはネイティブ対応）、クロスリージョンレプリケーション。Parameter Storeは安価だがローテーション機能なし。
試験のツボ
  • 「リージョンを制限、ただしIAMなどグローバルサービスは除外」→ SCPで aws:RequestedRegion ＋ NotAction。
  • 「組織外からS3にアクセスさせない」→ バケットポリシーの aws:PrincipalOrgID（多数バケットならRCP）。
  • SCPで管理アカウントは制御不可 → ワークロードを管理アカウントに置かない。
TASK 1.3

信頼性と回復性の高いアーキテクチャ

RPO/RTOとコストのトレードオフでDR戦略を選ぶ。

この章の考え方
DRとは、「どれだけ止まってよいか（RTO）」と「どれだけのデータを失ってよいか（RPO）」を業務側と合意し、それを満たす最も安い方式を選ぶ作業。すべてをマルチサイトにするのは過剰投資で、試験でも「要件を満たす最安」が正解になりやすい。
場面で理解する

バックアップ&復元

場面
社内の経費精算システム。1日止まっても手作業で回せる。
困りごと
待機環境を常時動かすのはもったいない。
解決
定期バックアップを別リージョンにコピーしておき、災害時はIaCで環境を作って復元する。
メリット
平常時のコストは、ほぼバックアップの保管料だけで済む。
注意
復旧手順をIaC化して定期的に訓練しておかないと、時間内に戻せない。

パイロットライト

場面
受発注システム。半日以内に復旧し、データは数分前まで戻したい。
困りごと
バックアップからの復元では、データの鮮度が足りない。
解決
DBだけは常時レプリケーションし、サーバーは停止したまま（AMIとIaCだけ用意）にしておく。
メリット
データは新しいまま、コンピュートの費用はほぼゼロ。
注意
起動とスケールに時間がかかる。AMIや設定の更新漏れに注意する。

ウォームスタンバイ

場面
ECサイト。停止は15分までしか許されない。
困りごと
ゼロから起動するのでは間に合わない。
解決
DR側で縮小版の本番環境を常に稼働させ、切り替え時にスケールアウトする。
メリット
常に動いているので切り替えが確実で、すぐに拡張できる。
注意
縮小版の分、常時コストがかかる。

マルチサイト（アクティブ/アクティブ）

場面
決済や証券取引。停止が即損失と信用の失墜につながる。
困りごと
切り替えにかかる数分すら許されない。
解決
複数のリージョンでフル稼働させ、平常時から両方でトラフィックを処理する。
メリット
ほぼ無停止。平常時も、利用者に近いリージョンで処理できるので遅延が小さい。
注意
コストは最も高い。両方で書き込むと競合するので、データの設計が必要（DynamoDBグローバルテーブルなど）。

Aurora Global Database

場面
ウォームスタンバイやマルチサイトで、RDBのデータをリージョン間でほぼリアルタイムに保ちたい。
困りごと
DBの論理レプリケーションは、遅延が大きいうえに本番の負荷も増える。
解決
ストレージ層で別リージョンへ複製し、有事にはセカンダリを昇格する。
メリット
遅延は通常1秒未満で、本番への負荷も小さい。昇格はおよそ1分。平常時はセカンダリで読み取り処理も受けられる。
注意
Aurora専用。セカンダリは基本的に読み取り専用（書き込み転送機能を除く）。

Global Accelerator（DNSに頼らない切り替え）

場面
リージョンを切り替えたのに、一部の利用者が古いリージョンに接続し続ける。
困りごと
利用者側のDNSキャッシュが、TTLを守らずに古い応答を使い続ける。
解決
固定のエニーキャストIPを入口にし、その裏の転送先をAWS側で切り替える。
メリット
IPアドレスが変わらないので、数十秒で確実に切り替わる。取引先のファイアウォールに登録するIPも2つで済む。
注意
HTTPのキャッシュ機能はない（その用途はCloudFront）。
仕組みと要点

4つのDR戦略

戦略RPO / RTO目安DRリージョンの状態コスト
バックアップ&復元数時間 / 数時間〜24hバックアップのみ。IaCで都度構築最安
パイロットライト数分 / 数十分〜数時間データは常時レプリケーション、コンピュートは停止（またはゼロ）安
ウォームスタンバイ秒〜分 / 分縮小版の本番環境が常時稼働。フェイルオーバー時にスケールアウト中
マルチサイト（アクティブ/アクティブ）ほぼゼロ / ほぼゼロフル稼働で両方がトラフィック処理高

データ層のレプリケーション

  • Aurora Global Database：ストレージレベルで通常1秒未満の遅延。セカンダリの昇格でRTO約1分。マネージドなスイッチオーバー（計画）/フェイルオーバー（非計画）。書き込み転送も可。
  • DynamoDB グローバルテーブル：マルチリージョン・マルチアクティブ。最終書き込み優先。強い整合性のマルチリージョン（MRSC）も選択可。
  • RDS クロスリージョンリードレプリカ：非同期。昇格は手動。
  • S3 CRR：非同期。S3 RTCで15分以内に99.99%を保証。

フェイルオーバーの仕組み

  • Route 53：ヘルスチェック＋フェイルオーバー/レイテンシー/加重ルーティング。
  • Application Recovery Controller (ARC)：ルーティングコントロールで確実な手動切替、リージョン切替計画、ゾーンシフト。
  • Global Accelerator：固定エニーキャストIP、数十秒でリージョン切替、DNSキャッシュの影響なし。
  • Elastic Disaster Recovery (DRS)：ブロックレベルの継続レプリケーション（RPO秒）、低コストのステージング領域、RTO分単位。オンプレ→AWS、リージョン間の両方。
フェイルオーバーの手順（図1-5）
  1. Route 53のヘルスチェックが東京のALBの異常を検知する（誤検知を避けたい場合はARCのルーティングコントロールで人が判断して切り替える）。
  2. Aurora Global Databaseのフェイルオーバーで、大阪のセカンダリを書き込み可能なプライマリに昇格させる（RTO 約1分）。
  3. 大阪のAuto Scalingの希望容量を 2 → 6 に増やす（ウォームスタンバイは稼働中なので数分で拡張できる）。
  4. Route 53がSECONDARY（大阪のALB）を返し、利用者の通信が大阪へ移る。DNSのTTLを待ちたくない場合はGlobal Acceleratorを使う。
試験のツボ
  • RDB で「RPO 1秒・RTO 1分・別リージョン」→ Aurora Global Database。
  • 「DNS TTLに依存せず即時切替」→ Global Accelerator。
  • DR先で「AMIとIaCを用意し、DBだけ常時レプリケーション」→ パイロットライト。
TASK 1.4

マルチアカウント環境の設計

ランディングゾーンを標準化し、アカウント作成を自動化する。

この章の考え方
アカウントは「壁」。1つのアカウントに全部を入れると、権限・コスト・障害の影響範囲（爆発半径）が混ざってしまう。適切に分けたうえで、分けたことで増える管理の手間を自動化で消すのがマルチアカウント戦略。
場面で理解する

アカウントの分割

場面
本番と開発が同じアカウントにあり、開発者の誤操作で本番DBが消えた。
困りごと
IAMだけで本番と開発を完全に分離するのは難しく、クォータ（上限値）やコストも混ざる。
解決
環境（本番・開発）やシステムごとにアカウントを分ける。
メリット
事故の影響範囲が限定される。コストはアカウント単位で見え、クォータも独立する。
注意
アカウントの数だけ管理対象が増える。そのため、下の各サービスで自動化する。

Control Tower

場面
これから全社でAWSを展開する。ベストプラクティスに沿った土台をすぐに用意したい。
困りごと
ログ・監査・SSO・ガードレールを手作業で組むと、数か月かかる。
解決
Control Towerでランディングゾーンを作り、新しいアカウントはAccount Factoryから払い出す。
メリット
数時間で標準的な環境が手に入り、新しいアカウントも最初から同じ状態で作られる。
注意
既存の独自環境に後から導入する場合は調整が必要。細かいカスタマイズはAFTやCfCTで行う。

CloudFormation StackSets

場面
全アカウントに、監査用のロール・Configルール・通知設定を配りたい。
困りごと
手作業で配ると漏れが出るうえ、新しいアカウントへの適用を忘れる。
解決
サービスマネージド型のStackSetsで、OU単位に自動デプロイする。
メリット
OUに追加されたアカウントに自動で展開され、更新も一括でできる。
注意
リージョンごとの展開順序と、失敗許容数を設計しておく。

VPC共有（RAM）

場面
各チームにVPCを作らせた結果、CIDRの重複、NAT Gatewayの乱立、設定のばらつきが起きた。
困りごと
ネットワークの専門知識がないチームにまで設計を任せている。
解決
ネットワークチームがVPCとサブネットを作り、RAMで各アカウントに共有する。
メリット
ネットワークは専門チームが統制し、アプリチームはアプリに集中できる。NATやエンドポイントを共用できるので、コストも下がる。
注意
参加者側のアカウントは、共有されたVPCのルートやNACLを変更できない（それが狙いでもある）。
仕組みと要点

AWS Organizations の構造

  • 推奨OU例：Security（ログアーカイブ、監査/セキュリティツール）、Infrastructure（ネットワーク、共有サービス）、Workloads（Prod/Non-Prod）、Sandbox、Suspended、Policy Staging。
  • 一括請求（Consolidated Billing）：ボリュームディスカウント、RI/SPの共有。
  • 委任管理者：管理アカウントを使わず、各サービスの管理を専用アカウントへ。

AWS Control Tower

  • ランディングゾーンを自動構築（管理・ログアーカイブ・監査アカウント、組織の証跡、IAM Identity Center）。
  • コントロール（ガードレール）：予防的＝SCP/RCP、検出的＝Config ルール、プロアクティブ＝CloudFormation Hooks。
  • Account Factory：Service Catalog 経由で標準アカウントを払い出し。AFT（Account Factory for Terraform）やCfCT（Customizations for Control Tower）でパイプラインによるカスタマイズ。

共有と一括展開

  • AWS RAM：サブネット、TGW、Resolverルール、License Manager 構成、Aurora DBクラスター（クローン）などを組織内で共有。
  • CloudFormation StackSets（サービスマネージド）：OU単位で展開し、自動デプロイで新規アカウントにも適用。IAMロールの手動作成不要。
試験のツボ
  • 「新規アカウントにも自動で」→ StackSets の自動デプロイ、Control Tower、委任管理者の自動有効化。
  • 「各アカウントがVPCを持つとCIDR管理が大変」→ VPC共有（RAM）＋ IPAM。
TASK 1.5

コストの可視化と最適化戦略

組織全体で「誰が何に使ったか」を見えるようにし、統制する。

この章の考え方
クラウドのコストは、「誰が何に使ったか」が見えなければ削減できない。まずタグとアカウントで見える化し、次に通知と自動制御を入れ、最後に購入オプションで割り引く、という順番で進める。
場面で理解する

コスト配分タグ

場面
月末の請求額が前月比+30%になったが、どのプロジェクトが原因か分からない。
困りごと
複数のプロジェクトが同じアカウントを使っていて、請求書では区別できない。
解決
Projectなどのタグを付け、支払いアカウントでコスト配分タグとして有効化する。
メリット
プロジェクト別・部門別に集計でき、社内の費用配賦（チャージバック）にも使える。
注意
有効化する前の期間には遡れない。付け忘れはタグポリシーやSCPで防ぐ。

Budgets アクション

場面
研修用のアカウントで、受講者がGPUインスタンスを起動したまま帰ってしまう。
困りごと
予算超過のアラートメールが来ても、対応は翌朝になる。
解決
しきい値を超えたら、SCPの適用やインスタンスの停止を自動で行う。
メリット
人が気づく前に費用の増加を止められる。
注意
本番アカウントで自動停止を使うと業務が止まるので、承認付きにするか通知だけにする。

Cost Anomaly Detection

場面
設定ミスでNAT Gatewayの転送量が急増したのに、月末の請求まで誰も気づかなかった。
困りごと
予算のしきい値に達するまでは、アラートが出ない。
解決
機械学習で、普段と違う支出のパターンを検知する。
メリット
しきい値を決めなくても、数日以内に異常に気づける。
注意
学習期間が必要。通知先をチームごとに分けておく。

CUR（Data Exports）＋Athena

場面
経営層から「サービス別・事業部別・日別」の詳細なコストレポートを求められた。
困りごと
Cost Explorerの画面だけでは、自社独自の切り口で集計できない。
解決
最も細かい粒度の請求データをS3に出力し、AthenaとQuickSightで分析する。
メリット
リソース単位・時間単位まで、自由な切り口で集計できる。
注意
データ量が大きいので、パーティションと列指向形式（Parquet）で出力する。
仕組みと要点
  • コスト配分タグ：ユーザー定義タグは管理（支払い）アカウントで有効化しないとCost Explorer/CURに出ない。有効化以前には遡らない。
  • タグポリシー（Organizations）：タグキー/値の表記ゆれを標準化。SCPで「タグなし作成を拒否」すれば強制。
  • AWS Cost and Usage Report / Data Exports：最も詳細なデータ。S3出力 → Athena/QuickSight で分析。
  • AWS Budgets：しきい値アラート。Budgets アクションで超過時にIAM/SCPポリシー適用やEC2/RDS停止を自動化。
  • Cost Anomaly Detection：機械学習で異常な支出を検知・通知。
  • RI/Savings Plans の共有：既定で組織内共有。特定アカウントを除外したい場合は請求設定で割引共有をオフ。
  • コストカテゴリ：アカウント・タグ等を組み合わせて事業部単位に集計。
試験のツボ
  • 「タグを付けたのにCost Explorerに出ない」→ コスト配分タグの有効化。
  • 「予算超過で自動的に新規リソース作成を止める」→ Budgets アクション（SCP適用）。
TASK 2.1

ビジネス要件を満たすデプロイ戦略

IaCとCI/CDで、安全に・繰り返し・ロールバック可能にリリースする。

この章の考え方
リリースで一番怖いのは、「全部を入れ替えてから、壊れていることに気づく」こと。少しずつ流し、異常があれば自動で戻す仕組みを作れば、リリースの頻度を上げても安全を保てる。
場面で理解する

カナリア / 線形デプロイ

場面
決済APIの更新。バグがあれば全利用者に影響する。
困りごと
一斉に切り替えると、問題に気づいたときには全員が影響を受けている。
解決
まず10%のトラフィックだけを新バージョンに流し、問題がなければ残りも移す。
メリット
問題があっても影響は一部の利用者だけ。CloudWatchアラームと連動して自動でロールバックできる。
注意
新旧のバージョンが同時に動くので、DBのスキーマは両方と互換にしておく。

ブルー/グリーン

場面
大型のアップデート。問題が起きたら数秒で元に戻したい。
困りごと
インプレースで更新すると、戻すにも再デプロイが必要になる。
解決
新しい環境（グリーン）を別に用意し、テスト後に入口を切り替える。
メリット
旧環境を残しておけば、即座に切り戻せる。本番と同じ環境で事前にテストできる。
注意
一時的に2倍のリソースが必要になる。

イミュータブルインフラ

場面
サーバーに手作業でパッチや設定変更を重ねた結果、1台1台の構成がばらばらになった。
困りごと
どのサーバーが正しい状態なのか、誰も分からない。
解決
変更は既存サーバーに当てず、新しいイメージから作り直して入れ替える。
メリット
全台が常に同じ状態になり、再現性が高い。
注意
起動の速いイメージと、ステートレスな設計が前提。

IaC（CloudFormation / CDK）

場面
検証環境で問題なかった変更が、本番で失敗した。調べると設定が違っていた。
困りごと
手作業で作った環境は、微妙に違ってしまう。
解決
同じテンプレートから全環境を作る。
メリット
環境を確実に再現でき、変更をコードレビューできる。DR環境もすぐに作れる。
注意
コンソールで手動変更するとドリフトが起きる。ドリフト検出で監視する。

Service Catalog

場面
開発者から「EC2を作ってほしい」という依頼が毎日届き、インフラ部門がボトルネックになっている。
困りごと
開発者に直接作成権限を渡すと、ルール違反の構成が生まれる。
解決
承認済みのテンプレートを製品として登録し、起動制約を付けてセルフサービスにする。
メリット
開発者は待たずに作れ、しかも承認済みの構成しか作れない。
注意
製品のバージョン管理と更新の運用が必要。
仕組みと要点

デプロイ方式

方式内容対応
インプレース / ローリング既存インスタンスを順次更新CodeDeploy (EC2)、Elastic Beanstalk
イミュータブル新しいインスタンス群を作成して入れ替えElastic Beanstalk
ブルー/グリーン新環境へ一括または段階的に切替、即時ロールバックCodeDeploy (EC2/ECS)、Route 53加重、ALB加重ターゲットグループ
カナリア / 線形一部トラフィックから段階的に移行CodeDeploy (Lambda エイリアス / ECS)、API Gateway カナリア

CodeDeploy はCloudWatch アラームと連動した自動ロールバックが可能。Lambda はエイリアスの加重ルーティングで段階移行。

CloudFormation の重要機能

  • DeletionPolicy（Retain / Snapshot / Delete）と UpdateReplacePolicy：スタック削除や置換時のデータ保護。
  • 変更セット：適用前に差分確認。スタックポリシー：特定リソースの更新禁止。終了保護。
  • カスタムリソース（Lambda）：CFN非対応の処理を組み込む。ドリフト検出で手動変更を検知。
  • AWS CDK：プログラミング言語でIaC、CFNに合成。

セルフサービスと標準化

  • Service Catalog：承認済み製品（CFNテンプレート）をポートフォリオで配布。起動制約で利用者に強い権限を与えずに作成可能。
  • Systems Manager：Run Command、State Manager、Automation ランブック。
試験のツボ
  • 「エラー率上昇で自動ロールバック」→ CodeDeploy＋CloudWatch アラーム。
  • 「開発者に管理者権限を与えず承認済み構成のみ作らせる」→ Service Catalog＋起動制約。
TASK 2.2

事業継続性を確保するソリューション

バックアップ・データ保護・ランサムウェア対策。DR戦略の詳細は1.3を参照。

この章の考え方
障害や災害だけでなく、ランサムウェア・内部不正・誤操作が起きても「データを戻せる」ことが事業継続の核になる。バックアップは「取れている」ことより、「戻せる」「消されない」ことが重要。
場面で理解する

AWS Backup による一元管理

場面
EBS・RDS・EFS・DynamoDBのバックアップ設定がチームごとにばらばらで、本当に取れているのか誰も把握していない。
困りごと
サービスごとに設定画面も保持の仕組みも違う。
解決
バックアッププランを組織のバックアップポリシーで全アカウントに適用する。
メリット
1つのポリシーで組織全体をカバーでき、準拠状況もレポートで確認できる。
注意
復元テストは別途計画して、定期的に実施する。

クロスアカウントコピー＋Vault Lock

場面
ランサムウェア攻撃で管理者権限を奪われ、バックアップまで消された（実際によくある手口）。
困りごと
同じアカウントにあるバックアップは、管理者権限があれば消せる。
解決
別のアカウントにコピーし、そのボールトをコンプライアンスモードでロックする。
メリット
本番アカウントが全滅しても、データを戻せる。
注意
コンプライアンスモードは解除できない。保持期間を誤ると、不要なデータも消せずにコストが増える。

ポイントインタイムリカバリ（PITR）

場面
作業ミスで、今日の14:05に重要なテーブルを削除してしまった。
困りごと
夜間バックアップから戻すと、今日1日分のデータが失われる。
解決
RDS/AuroraやDynamoDBのPITRで、14:04の状態に戻す。
メリット
秒単位で、直前の状態に戻せる。
注意
RDSの復元は別のインスタンスとして作られるので、接続先の切り替えが必要。

Elastic Disaster Recovery

場面
オンプレミスのサーバー200台のために、別のデータセンターを借りるのは高すぎる。
困りごと
待機用の設備を常に維持するコストが大きい。
解決
AWSを待機サイトにし、ブロックレベルで継続的に複製しておく。
メリット
平常時は安価なステージング環境だけで済み、有事のときだけフル稼働の料金を払う。
注意
定期的にドリル（訓練用の起動）を行い、手順を確認しておく。
仕組みと要点
  • AWS Backup：多サービスのバックアップを一元化。バックアッププランでクロスリージョン／クロスアカウントコピー。Organizations のバックアップポリシーで組織展開。
  • Backup Vault Lock：コンプライアンスモードでルートユーザーでも削除不可（WORM）。ランサムウェア・内部不正対策。論理エアギャップボールトも選択肢。
  • S3：バージョニング＋MFA Delete、Object Lock、CRR/SRR。
  • RDS/Aurora：自動バックアップ（PITR、最大35日）、クロスリージョン自動バックアップ複製、Aurora バックトラック（MySQL互換）。
  • Elastic Disaster Recovery：オンプレやEC2を秒単位RPOで継続レプリケーション、低コストのステージング。
RPO/RTOの考え方：RPO＝どれだけ過去のデータまで戻れればよいか（データ損失許容）。RTO＝どれだけで復旧すべきか（停止許容）。数値が小さいほど高コスト。
試験のツボ
  • 「管理者も削除できないバックアップ」→ Vault Lock（コンプライアンスモード）＋別アカウントへのコピー。
  • 「オンプレのサーバー群、RPO秒・RTO分・低コスト」→ Elastic Disaster Recovery。
TASK 2.3

新規ソリューションのセキュリティ制御

エッジ保護・認証・データ保護を組み合わせる。

この章の考え方
入口を絞る・中身を暗号化する・相手を確かめる、の3層で守る。1つが破られても次の層で止める多層防御が、Proで問われるセキュリティ設計。
場面で理解する

CloudFront＋OAC

場面
S3の画像を配信するため、S3をパブリックにした。
困りごと
S3のURLを直接叩かれるうえ、WAFも効かない。
解決
S3は非公開のままにし、CloudFrontからOAC経由でだけ読めるようにする。
メリット
入口がCloudFrontの1つに絞られ、キャッシュで高速化とS3のリクエスト費の削減もできる。
注意
バケットポリシーとKMSのキーポリシーの両方で、CloudFrontを許可する必要がある。

署名付きURL / Cookie

場面
有料会員限定の動画を配信したい。
困りごと
URLが共有されると、誰でも見られてしまう。
解決
有効期限付きの署名をURL（1ファイル）またはCookie（複数ファイル）に付ける。
メリット
期限が切れれば無効になり、会員以外はアクセスできない。
注意
署名に使う鍵の管理とローテーションが必要。

AWS WAF

場面
ログイン画面への総当たり攻撃や、SQLインジェクションの試行が続いている。
困りごと
アプリを改修して対策するには時間がかかる。
解決
WAFのマネージドルールとレートベースルールを、CloudFrontやALBに適用する。
メリット
アプリを変更せずにL7の攻撃をブロックでき、大量アクセスの制限もできる。
注意
誤検知で正規の利用者を止めないよう、最初はカウントモードで様子を見る。

Shield Advanced

場面
大型セールの当日にDDoS攻撃でサイトが落ちたら、損失が非常に大きい。
困りごと
攻撃を受けて自動スケールすると、費用も膨らむ。
解決
Shield Advancedで保護対象のリソースを登録する。
メリット
専門チーム（SRT）の支援を受けられ、攻撃で増えた費用も補償される。
注意
月額の固定料金と1年契約が必要。

Amazon Cognito

場面
自社アプリに、会員登録・ログイン・SNSログインを付けたい。
困りごと
認証基盤を自前で作ると、パスワード管理・MFA・脆弱性対応の負担が大きい。
解決
ユーザープールで認証し、必要ならIDプールでAWSの一時的な権限を発行する。
メリット
認証の実装と運用をAWSに任せられる。
注意
ユーザープールとIDプールの役割の違いは、試験で頻出。

VPCエンドポイント（ポリシー付き）

場面
社内規定で「データはインターネットを経由させない」「社外のバケットへ持ち出させない」と決まっている。
困りごと
NAT経由だと、どのバケットにも書き込めてしまう。
解決
S3のゲートウェイエンドポイントを使い、エンドポイントポリシーで自社のバケットだけを許可する。
メリット
プライベートな経路のまま、データの持ち出しも防げる。
注意
バケット側でも aws:SourceVpce の条件を付けて、両方向から絞る。
仕組みと要点

エッジとアプリケーション保護

  • CloudFront＋OAC（オリジンアクセスコントロール）：S3を非公開のままCloudFront経由でのみ配信。SSE-KMSにも対応（旧OAIは非推奨）。
  • 署名付きURL＝1ファイル単位、署名付きCookie＝複数ファイル（有料会員エリア全体など）。
  • AWS WAF：SQLi/XSS、レートベースルール、Bot Control、地理的制限。CloudFront・ALB・API Gateway・AppSyncに適用。Firewall Manager で組織一括適用。
  • Shield Advanced：L3/4/7のDDoS保護、DDoSコスト保護、SRT（Shield Response Team）支援。

認証・認可

  • Cognito ユーザープール：アプリのユーザー認証（サインアップ/サインイン、ソーシャル/SAML連携）→ JWT。
  • Cognito アイデンティティプール：AWSの一時認証情報を発行（S3直接アップロードなど）。
  • ALBの認証アクション（OIDC/Cognito）でアプリ改修なしに認証を追加。

ネットワーク内のデータ保護

  • VPCエンドポイント（ゲートウェイ型：S3/DynamoDB、インターフェイス型：その他）＋エンドポイントポリシー。
  • S3バケットポリシーで aws:SourceVpce を条件にVPCエンドポイント経由のみ許可。
  • API Gateway プライベートAPI：インターフェイスエンドポイント経由のみ、リソースポリシーで制御。
試験のツボ
  • 「ソーシャルログインしたモバイルユーザーがS3に直接アップロード」→ Cognito アイデンティティプール。
  • 「DDoS攻撃によるスケールアウト費用の補償」→ Shield Advanced。
TASK 2.4

信頼性要件を満たす設計

疎結合・非同期・冪等性で障害を局所化する。

この章の考え方
サービス同士が直接呼び合っていると、1つの遅延が連鎖して全体が止まる。間にキューやイベントを挟めば、各サービスが自分のペースで動き、障害を局所化できる（疎結合）。
場面で理解する

SQS（緩衝材としてのキュー）

場面
セール開始の瞬間、注文が平常時の50倍に跳ね上がる。
困りごと
処理側が追いつかず、受付ごと落ちてしまう。
解決
受け付けた注文はキューに入れてすぐ応答し、処理側は一定のペースで消化する。
メリット
受付を落とさずに済み、処理側をピークに合わせて用意する必要もない。
注意
非同期なので即時に結果を返せない。重複配信を前提に、処理を冪等にする。

SNS→SQS ファンアウト

場面
注文が入ったことを、在庫・請求・配送・分析の各サービスに知らせたい。
困りごと
送り手が各サービスを直接呼ぶと、受け手が増えるたびにコードを変える必要がある。
解決
SNSに1回発行し、各サービスは自分専用のSQSキューで受け取る。
メリット
送り手は受け手を知らなくてよく、受け手を追加してもコードは変わらない。
注意
順序や重複排除が必要ならFIFO（SNS FIFO＋SQS FIFO）にする。

EventBridge

場面
SaaS（Zendeskなど）やAWSサービスのイベントで処理を起動し、内容に応じて振り分けたい。
困りごと
SNSでは、イベントの中身での細かい振り分けやSaaSとの連携に限界がある。
解決
イベントバスとルールで、パターンに一致したイベントをターゲットへ送る。
メリット
内容ベースのルーティング、アーカイブとリプレイ、別アカウントへの転送ができる。
注意
スループットや遅延の要件が厳しい場合は、SNSやKinesisを検討する。

Step Functions

場面
与信 → 在庫引当 → 決済 → 出荷の多段処理で、途中で失敗したら前の処理を取り消したい。
困りごと
制御ロジックがコードに埋もれ、失敗時の状態が分からなくなる。
解決
ワークフローとして定義し、リトライ・分岐・補償処理（取り消し）を宣言的に書く。
メリット
処理の状態が可視化され、失敗した箇所から再実行できる。人による承認待ちも組み込める。
注意
高頻度で短時間の処理にはExpressワークフローを使う（料金体系が違う）。

冪等性（べきとうせい）

場面
決済APIがタイムアウトしたので、クライアントが再送した結果、二重に課金された。
困りごと
ネットワーク越しの処理では、「届いたが応答が返らなかった」ことが起こりうる。
解決
リクエストに冪等キーを付け、同じキーの2回目以降は1回目の結果を返す。
メリット
安全にリトライでき、キューの重複配信にも耐えられる。
注意
キーの保存先（DynamoDBなど）と保存期間の設計が必要。
仕組みと要点
サービス使いどころ要点
SQS 標準バッファリング、負荷平準化少なくとも1回配信、順序保証なし。可視性タイムアウト、DLQ
SQS FIFO順序と重複排除が必要メッセージグループID単位で順序保証、並列度もグループ単位
SNSファンアウト（1対多）SNS→複数SQSでファンアウト、サブスクリプションフィルターポリシー
EventBridgeイベント駆動、SaaS連携、クロスアカウントルールでパターンマッチ、アーカイブ/リプレイ、Pipes
Step Functionsワークフロー、長時間処理Standard＝最大1年・厳密1回、Express＝高スループット短時間。タスクトークンで人手承認待ち
Kinesis Data Streamsリアルタイムストリーム、順序（シャード単位）複数コンシューマーによる再読込
  • Auto Scaling：ターゲット追跡、予測スケーリング、ウォームプール。
  • Lambda：予約された同時実行（上限確保と制限）、プロビジョニング済み同時実行（コールドスタート回避）。
  • API Gateway：スロットリング、使用量プラン、キャッシュ。
  • リトライは指数バックオフ＋ジッター、処理は冪等に。
試験のツボ
  • 「顧客ごとに順序を守りつつ並列処理」→ SQS FIFO、MessageGroupId＝顧客ID。
  • 「数日かかる承認プロセス」→ Step Functions Standard＋タスクトークン（コールバック）。
TASK 2.5

パフォーマンス目標を満たす設計

キャッシュ・エッジ・適材適所のデータストア。

この章の考え方
遅さの原因は、距離（利用者から遠い）・計算（処理が重い）・待ち（DB接続や同じデータの読み込み）のどれかにほぼ分けられる。原因に合った手段を選ぶことが大切。
場面で理解する

CloudFront（距離の解消）

場面
海外の利用者から、ページの表示が遅いと言われる。
困りごと
東京のサーバーまで、毎回地球の反対側から通信している。
解決
世界中のエッジロケーションでコンテンツをキャッシュする。
メリット
表示が速くなり、オリジンへの負荷と転送量も減る。
注意
個人ごとに変わる動的なページは、キャッシュキーの設計が必要。

Global Accelerator

場面
オンラインゲームやVoIPなど、キャッシュできないTCP/UDPの通信を世界中から受ける。
困りごと
インターネット経由だと、経路が不安定で遅延がばらつく。
解決
最寄りのエッジから、AWSのバックボーン網を通ってリージョンへ運ぶ。
メリット
遅延が安定し、固定IPなので取引先のファイアウォール登録も簡単になる。
注意
コンテンツのキャッシュはしない。

ElastiCache

場面
ランキングや商品詳細を表示する同じクエリが、DBに毎秒数千回届く。
困りごと
同じ結果を何度も計算して、DBのCPUが張り付いている。
解決
結果をインメモリのキャッシュに置き、DBより先に参照する。
メリット
応答がミリ秒未満になり、DBを大きくせずに済む。
注意
キャッシュと元データの食い違いに注意（TTLと無効化の設計）。

RDS Proxy

場面
Lambdaが同時に1,000実行されると、DBの接続数の上限に達する。
困りごと
Lambdaは実行環境ごとに接続を作るので、接続数が膨れ上がる。
解決
RDS Proxyで接続をプールし、共有する。
メリット
接続エラーがなくなり、フェイルオーバーも速くなる。IAM認証にも対応する。
注意
プロキシの料金がかかる。

目的別ストレージ

場面
HPCでS3上の大量データを並列処理したい、またはWindowsのファイルサーバーを移行したい。
困りごと
汎用のストレージでは、性能やプロトコルが合わない。
解決
HPCにはFSx for Lustre、WindowsにはFSx for Windows File Server、NetAppにはFSx for ONTAPを使う。
メリット
要件に最適化された性能と機能を、マネージドで使える。
注意
何でもEFSやS3にしない。「プロトコル」と「性能要件」で選ぶ。
仕組みと要点

キャッシュとエッジ

  • CloudFront：HTTP(S)コンテンツ、動的配信も可。キャッシュポリシー、Lambda@Edge / CloudFront Functions。
  • Global Accelerator：TCP/UDP、固定エニーキャストIP×2、AWSバックボーン経由で低遅延。ゲーム・VoIP・IP許可リストが必要なB2B。
  • ElastiCache：Redis OSS/Valkey（永続化・レプリケーション・データ構造）、Memcached（シンプル・マルチスレッド）。
  • DAX：DynamoDB専用のインメモリキャッシュ、マイクロ秒の読み取り、コード変更最小。
  • RDS Proxy：接続プーリング。Lambdaからの大量接続、フェイルオーバー時間短縮、IAM認証。

ストレージ

要件選択
Linux共有ファイル、自動拡張Amazon EFS
Windows SMB、AD統合、DFSFSx for Windows File Server
HPC、ミリ秒未満、S3と連携FSx for Lustre
NFS/SMB/iSCSI混在、NetAppの機能（SnapMirror等）FSx for NetApp ONTAP
高IOPSブロックEBS io2 Block Express（gp3はIOPS/スループットを容量と独立に設定）
  • S3：マルチパートアップロード、Transfer Acceleration（遠隔地からのアップロード）、プレフィックス分散。
試験のツボ
  • 「UDP」「固定IP」→ Global Accelerator。CloudFrontはHTTP(S)。
  • 「Lambdaからのデータベース接続枯渇」→ RDS Proxy。
TASK 2.6

コスト最適化を組み込んだ設計

購入オプションとアーキテクチャの両面で削る。

この章の考え方
「ずっと使う分は予約で割り引く・変動分はオンデマンド・中断してよい分はスポット」と、使い方で買い方を分けるのが基本。さらに、そもそも払わなくてよい料金（NAT経由の転送など）を設計で消す。
場面で理解する

Savings Plans

場面
24時間365日動くWebシステムがある。
困りごと
オンデマンドのままでは、定価を払い続けることになる。
解決
1年または3年の利用額をコミットする。
メリット
最大72%の割引。Compute Savings Plansなら、EC2からFargateやLambdaへ移っても割引が続く。
注意
使わなくても支払いが発生する。コミット額は、過去の利用実績の下限に合わせる。

スポットインスタンス

場面
夜間バッチ、CI/CDのビルド、機械学習の学習ジョブ。
困りごと
オンデマンドで回すと高い。
解決
AWSの余剰キャパシティを、スポットで安く使う。
メリット
最大90%の割引。
注意
2分前の通知で中断される。チェックポイントを取り、複数のインスタンスタイプに分散させる。

S3ライフサイクル / Intelligent-Tiering

場面
監査用のログを7年間保管する。よく見るのは最初の1か月だけ。
困りごと
全期間Standardのままだと、保管料が膨らむ。
解決
ライフサイクルで Standard → Standard-IA → Glacier Deep Archive と移動させる。アクセスパターンが読めないならIntelligent-Tieringにする。
メリット
保管料を数十分の一にできる。
注意
取り出し料金、最低保存期間、取り出しにかかる時間を確認しておく。

ゲートウェイ型VPCエンドポイント

場面
バッチ処理がS3と毎日数十TBをやりとりし、NAT Gatewayの処理料金が大きい。
困りごと
NATは、処理したデータ量に応じて課金される。
解決
S3（またはDynamoDB）のゲートウェイ型エンドポイントを作り、ルートテーブルに追加する。
メリット
エンドポイントは無料で、NATの処理料金が丸ごとなくなる。
注意
同じリージョンのS3/DynamoDB限定。他のサービスはインターフェイス型（有料）になる。

Graviton

場面
Java/Python/Node.jsなどの一般的なWebアプリを、EC2やLambdaで動かしている。
困りごと
x86のインスタンスでは、価格性能比に限界がある。
解決
ARMベースのGravitonインスタンスに移行する。
メリット
同等の性能をより安く得られる（価格性能比は最大40%向上）。
注意
ARMに対応したライブラリとコンテナイメージが必要。
仕組みと要点
購入オプション割引柔軟性
Compute Savings Plans最大66%EC2（ファミリー・リージョン・OS問わず）＋Fargate＋Lambda

  • S3ストレージクラス：Standard → Standard-IA / One Zone-IA → Glacier Instant / Flexible / Deep Archive。アクセスパターン不明ならIntelligent-Tiering。ライフサイクルルールで移行・削除。
  • データ転送：プライベートサブネットからS3/DynamoDBはゲートウェイ型VPCエンドポイント（無料）でNAT処理料金を削減。
  • Graviton（ARM）で価格性能比向上、サーバーレスでアイドル課金ゼロ。
試験のツボ
  • 「EC2・Fargate・Lambda混在、将来構成が変わる」→ Compute Savings Plans。
  • 「中断されても再実行できるバッチ」→ スポット（AWS Batch / EC2 Fleet）。
TASK 3.1

運用上の優秀性の改善

観測・自動化・修復を仕組みにする。

この章の考え方
人が気づいて人が直す運用は、規模が大きくなると回らない。「検知 → 通知 → 自動修復」をつなぎ、人は判断が必要なことだけに集中するのが運用上の優秀性。
場面で理解する

CloudWatch クロスアカウントオブザーバビリティ

場面
障害のたびに、30アカウントのコンソールを行き来して原因を探している。
困りごと
情報がアカウントごとに分散している。
解決
監視用アカウントに、全アカウントのメトリクス・ログ・トレースを集約して参照する。
メリット
1か所で横断的に調べられ、復旧までの時間が短くなる。
注意
ログの保持と料金はソースアカウント側に残る。

X-Ray（分散トレーシング）

場面
「ときどき遅い」と言われるが、10個あるマイクロサービスのどれが原因か分からない。
困りごと
各サービスのログを見ても、1つのリクエストの全体像がつながらない。
解決
リクエストにトレースIDを付け、経路と各区間の所要時間を記録する。
メリット
ボトルネックがサービスマップ上で一目で分かる。
注意
サンプリング率を調整して、コストと情報量のバランスを取る。

Session Manager

場面
踏み台サーバーとSSH鍵を管理しているが、誰が何を操作したかの記録が残らない。
困りごと
ポートを開ける必要があり、鍵が漏れるリスクもある。
解決
SSMエージェント経由で、ブラウザやCLIからシェルに接続する。
メリット
インバウンドのポート開放が不要になり、IAMで制御でき、操作ログもS3やCloudWatchに残る。
注意
プライベートサブネットで使う場合は、SSM用のVPCエンドポイントが必要。

Config ルール＋自動修復

場面
誰かがうっかりS3バケットをパブリックにしてしまう。
困りごと
人手の定期チェックでは、発見が数日遅れる。
解決
Configルールで違反を検出し、SSM Automationで自動的に修正する。
メリット
数分で安全な状態に戻り、履歴も残る。
注意
自動修復は影響範囲を確認してから有効化する。まずは検出だけで運用を始める。

Patch Manager

場面
毎月のOSパッチを、500台に手作業で当てている。
困りごと
作業に漏れが出るうえ、適用状況を報告できない。
解決
パッチベースラインとメンテナンスウィンドウで自動適用する。
メリット
適用が自動化され、準拠状況を一覧で報告できる。
注意
本番より先に検証環境へ適用する段階的な運用にする。
仕組みと要点
  • CloudWatch：メトリクス、Logs Insights、異常検出、複合アラーム、Synthetics（外形監視）、クロスアカウントオブザーバビリティ（モニタリングアカウントに集約）。
  • X-Ray / ADOT：分散トレーシングでマイクロサービスのボトルネック特定。
  • Systems Manager：Session Manager（SSH/踏み台不要、ログ記録）、Patch Manager（パッチベースライン＋メンテナンスウィンドウ）、Automation（ランブック）、OpsCenter、Fleet Manager。Quick Setupで組織展開。
  • AWS Config＋自動修復：ルール違反時にSSM Automation を実行（例：パブリックS3ブロック、暗号化有効化）。
  • EventBridge：サービスイベントをトリガーに自動対処。
試験のツボ
  • 「SSHポートを開けずに運用・操作ログを監査」→ Session Manager。
  • 「設定違反を検出して自動修正」→ Config ルール＋自動修復（SSM Automation）。
TASK 3.2

セキュリティの改善

既存環境の弱点を見つけ、最小権限と自動対応へ寄せる。

この章の考え方
既存の環境には、昔作った強すぎる権限や長期キーが残っている。使っていないものを消す・長期の鍵を一時的な鍵に替える・異常時は自動で隔離する、の順で安全にしていく。
場面で理解する

IAMロール（一時認証情報）への置き換え

場面
アクセスキーを誤ってGitHubにpushしてしまい、数分で悪用された。
困りごと
長期のアクセスキーは、漏れたら無効化するまで使われ続ける。
解決
EC2はインスタンスプロファイル、オンプレミスはIAM Roles Anywhere、CI/CDはOIDC連携で一時的な認証情報を使う。
メリット
漏れても短時間で失効し、ローテーションの運用も不要になる。
注意
古いキーは、利用状況（最終使用日時）を確認してから無効化する。

IAM Access Analyzer

場面
5年前に作られたロールにAdministratorAccessが付いているが、誰が使っているか分からない。
困りごと
外すと何かが壊れそうで、誰も触れない。
解決
未使用のアクセスを検出し、CloudTrailの実績から最小権限のポリシーを生成する。
メリット
根拠をもって権限を削れる。
注意
月末処理のように、たまにしか使われない権限もあるので、十分な期間の実績で判断する。

IMDSv2の強制

場面
WebアプリのSSRF脆弱性を突かれ、インスタンスメタデータから認証情報を盗まれる（過去に大手金融機関の大規模漏えいで使われた手口）。
困りごと
アプリの修正には時間がかかる。
解決
IMDSv2（セッショントークン必須）を強制し、SCPで新規の起動にも義務付ける。
メリット
アプリを直さなくても、インフラ側でこの攻撃を防げる。
注意
古いSDKやツールがIMDSv1に依存していないか、事前に確認する。

検出結果からの自動隔離

場面
深夜にGuardDutyが暗号通貨のマイニングを検知したが、担当者が気づいたのは翌朝だった。
困りごと
その間も課金と被害が続いた。
解決
EventBridgeで検出結果を受け、スナップショットを取得してから隔離用のセキュリティグループに付け替える。
メリット
数分で封じ込めができ、しかも調査用の証拠も残る。
注意
いきなりインスタンスを終了すると、証拠が消える。
仕組みと要点
  • 長期認証情報の排除：EC2はインスタンスプロファイル（IAMロール）、オンプレはIAM Roles Anywhere、DBパスワードはSecrets Manager＋自動ローテーション。
  • IAM Access Analyzer：外部共有の検出、未使用アクセスの検出、CloudTrailからの最小権限ポリシー生成、ポリシー検証。
  • IMDSv2の強制：SSRFによるメタデータ窃取対策（起動テンプレートやSCPで強制）。
  • 自動対応：GuardDuty検出結果 → EventBridge → Lambda / Step Functions / SSM Automation（隔離用SGに付け替え、スナップショット取得）。
  • Amazon Inspector（EC2/ECR/Lambdaの脆弱性）、Security Hub（CSPM・統合）、Detective（調査）。
試験のツボ
  • 「侵害されたインスタンスを証拠保全しつつ自動隔離」→ EventBridge で自動化、SGを隔離用に変更、EBSスナップショット。
TASK 3.3

パフォーマンスの改善

計測してからボトルネックに手を打つ。

この章の考え方
推測でサイズを上げる前に、計測してボトルネックを特定する。多くの場合、原因はDBへの読み取りの集中か、キャッシュが効いていないことにある。
場面で理解する

Performance Insights

場面
DBのCPUが100%に張り付いているが、どのSQLが原因か分からない。
困りごと
インスタンスを大きくしても、すぐまた張り付く。
解決
待機イベントと上位のSQLを可視化する。
メリット
原因のSQLを特定し、インデックスやクエリを改善できる。
注意
長期間の履歴を保持するには有料の設定が必要。

読み取りの分離（リードレプリカ）

場面
月末の集計レポートを実行すると、受注処理が遅くなる。
困りごと
重い読み取り処理と更新処理が、同じインスタンスを奪い合っている。
解決
Auroraレプリカを追加し、レポートはリーダーエンドポイントやカスタムエンドポイントに向ける。
メリット
受注処理に影響を与えずにレポートを実行できる。
注意
レプリカのデータはわずかに遅れる可能性がある。

Aurora Serverless v2

場面
平日の日中だけ忙しい社内システムのDB。
困りごと
ピークに合わせたサイズで24時間動かしている。
解決
容量（ACU）が負荷に応じて自動で伸縮するようにする。
メリット
ピーク時は十分な性能が出て、夜間はほぼ最小の課金になる。
注意
常に高負荷なら、プロビジョンドのインスタンスの方が安い。

CloudFrontのキャッシュキー最適化

場面
CloudFrontを入れたのに、速くならず、オリジンの負荷も下がらない。
困りごと
不要なヘッダーやCookieまでキャッシュキーに含まれ、同じ内容が別物として扱われている。
解決
キャッシュポリシーで、キーを本当に必要な値だけに絞る。
メリット
キャッシュヒット率が上がり、オリジンの負荷とコストが下がる。
注意
オリジンに渡す必要がある値は、オリジンリクエストポリシーで別に転送する。
仕組みと要点
  • RDS Performance Insights / CloudWatch Database Insights：待機イベントや上位SQLを特定。
  • 読み取り負荷 → リードレプリカ（Auroraはリーダーエンドポイント）、キャッシュ（ElastiCache）。
  • 予測困難な負荷 → Aurora Serverless v2（ACU単位で秒単位スケール）、DynamoDBオンデマンド。
  • CloudFront キャッシュヒット率改善：キャッシュキーから不要なヘッダー/クエリ/Cookieを除外（キャッシュポリシー）、オリジンリクエストポリシーで必要なものだけ転送、Origin Shield。
  • Compute Optimizer：インスタンスタイプ・EBS・Lambdaメモリの推奨。
TASK 3.4

信頼性の改善

単一障害点を消し、失敗を前提に設計し直す。

この章の考え方
目指すのは「壊れない」ではなく、「壊れても全体は止まらない」こと。1つしかないもの（単一障害点）を探して潰し、実際に壊して確かめる。
場面で理解する

ステートレス化（セッションの外出し）

場面
スケールインのたびに、ユーザーがログアウトされる。
困りごと
セッション情報が各サーバーのメモリにあるため、サーバーを自由に増減できない。
解決
セッションをElastiCacheやDynamoDBに置く。
メリット
どのサーバーでもリクエストを処理でき、自由にスケールできる。
注意
セッションストア自体も冗長化しておく。

Multi-AZ化

場面
DBが1台構成で、メンテナンスや障害のたびに停止している。
困りごと
AZの障害やハードウェアの故障が、そのままサービスの停止になる。
解決
RDS Multi-AZ（またはAuroraのレプリカ）で待機系を別のAZに置く。
メリット
障害時は自動でフェイルオーバーし、メンテナンス時の停止も短くなる。
注意
待機系の分のコストがかかる。

指数バックオフ＋ジッター

場面
障害から復旧した直後、全クライアントが一斉に再接続して、また落ちた。
困りごと
リトライのタイミングが揃ってしまい、負荷の波ができる。
解決
リトライの間隔を指数的に延ばし、ランダムな揺らぎ（ジッター）を加える。
メリット
負荷が時間的に分散され、復旧が安定する。
注意
リトライ回数の上限と、サーキットブレーカーも併用する。

AWS Fault Injection Service

場面
DRの手順書はあるが、一度も試したことがない。
困りごと
本当に障害が起きたときに初めて、手順の不備が分かる。
解決
停止条件付きの実験で、計画的にAZ障害やインスタンスの停止を起こす。
メリット
本番の障害が起きる前に、弱点を見つけて直せる。
注意
まずは検証環境で、影響範囲を限定した実験から始める。
仕組みと要点
  • 単一障害点：単一AZのNAT Gateway → AZごとにNAT Gateway＋AZ別ルートテーブル。単一インスタンスDB → Multi-AZ。
  • ステートレス化：セッションをElastiCache/DynamoDBへ外出しし、Auto Scaling可能に。
  • リトライストーム対策：指数バックオフ＋ジッター、サーキットブレーカー、SQSによる緩衝。
  • AWS Fault Injection Service (FIS)：制御されたカオスエンジニアリング（AZ障害、インスタンス停止、API遅延注入）。
  • AWS Resilience Hub：RPO/RTO目標に対する評価と改善提案。
TASK 3.5

コスト最適化の機会の特定

「使っていない」「大きすぎる」「高いクラス」を見つける。

この章の考え方
コスト削減は「止める → 小さくする → 安く買う」の順番で進める。先に割引を買ってしまうと、無駄に大きな構成のまま割引を固定してしまう。
場面で理解する

止める（スケジュール停止）

場面
開発環境が24時間動いているが、使うのは平日の日中だけ。
困りごと
使っていない時間も課金されている。
解決
Instance SchedulerやEventBridge Schedulerで、夜間と週末は停止する。
メリット
稼働時間が約1/3になり、約65%を削減できる。
注意
停止中に動くバッチなどがないか、事前に確認する。

小さくする（ライトサイジング）

場面
CPUの平均使用率が10%のインスタンスが大量にある。
困りごと
作った当時に「念のため」大きなサイズを選んでいた。
解決
Compute Optimizerの推奨をもとに、サイズを下げるかGravitonに移行する。
メリット
性能を保ったまま、コストを大きく下げられる。
注意
メモリの使用率はCloudWatchエージェントを入れないと見えない。

消す（放置リソースの削除）

場面
未アタッチのEBS、数年分のスナップショット、使っていないElastic IPが残っている。
困りごと
誰も消していいのか判断できず、残り続けている。
解決
Trusted AdvisorやCost Optimization Hubで検出し、Data Lifecycle Managerで世代管理を自動化する。
メリット
何も失わずに、確実に削減できる。
注意
パブリックIPv4アドレスは、使用中でも課金される点に注意する。

安く買う（最後に割引購入）

場面
構成の最適化が終わり、利用量が安定してきた。
困りごと
オンデマンドのままでは割高。
解決
最適化した後の利用量をもとに、Savings PlansやRIを購入する。
メリット
無駄のない構成に対して割引が効く。
注意
RDSやElastiCacheなどは、Savings Plansの対象外なのでRIで買う。
仕組みと要点
  • Compute Optimizer：過剰プロビジョニングの検出、Graviton移行推奨。
  • Trusted Advisor：アイドルのRDS/ロードバランサー、未関連付けのEIP、未使用EBS。
  • Amazon Data Lifecycle Manager：EBSスナップショット/AMIの世代管理・自動削除。
  • S3 Storage Lens：組織全体のストレージ利用・未完了マルチパート等の可視化。
  • 非本番環境の夜間・週末停止（Instance Scheduler、EventBridge Scheduler）。
  • Cost Optimization Hub：推奨を一元的に集約・優先順位付け。
TASK 4.1

移行対象ワークロードの選定

棚卸し → 依存関係把握 → 7Rで方針決定 → ビジネスケース。

この章の考え方
全部を同じやり方で移すのは失敗のもと。システムごとに「廃止する・残す・そのまま移す・少し直す・作り直す」を決め、効果の大きいものから順に、グループ（ウェーブ）ごとに移す。期限が厳しいときは「まずリホスト、後でモダナイズ」が定石。
場面で理解する

ディスカバリー（現状調査）

場面
サーバー台帳が古く、どのサーバーが何とつながっているか誰も知らない。
困りごと
一緒に移すべきサーバーを別々に移すと、移行後に通信が切れて障害になる。
解決
Application Discovery Serviceで、構成・利用率・通信の依存関係を実測する。
メリット
依存関係に基づいて移行ウェーブを組め、サイズの見積もりも実測値でできる。
注意
依存関係まで取るならエージェント型にする（エージェントレス型は構成と利用率が中心）。

7Rで方針を決める

場面
300システムの移行方針を決める必要がある。
困りごと
全部を作り直すと、時間も予算も足りない。
解決
期限が迫るものはリホスト、ライセンス削減の効果が大きいものはリプラットフォーム、競争力の源泉はリファクタ、使われていないものはリタイアにする。
メリット
投資を、効果の大きいところに集中できる。
注意
リテイン（残す）も正しい選択肢の1つ。

Migration Evaluator

場面
経営会議で「移行すると本当に安くなるのか」と問われた。
困りごと
カタログのスペックで見積もると、過大な見積もりになる。
解決
実際の利用状況を収集し、適正なサイズとライセンスの最適化を反映したTCOを出す。
メリット
データに基づく説得力のあるビジネスケースを作れる。
注意
収集期間が短いと、ピーク時の負荷を見落とす。
仕組みと要点

7つの移行戦略（7R）

戦略内容例
リタイア廃止利用者のいない旧システム
リテイン当面オンプレに残す更改直後、規制上移行不可
リホストそのまま移す（リフト&シフト）AWS MGNでサーバー移行
リロケートハイパーバイザーレベルで移すVMware環境の移設
リパーチェス製品を買い替え（SaaS化）自社CRM → SaaS CRM
リプラットフォーム軽微な最適化（リフト&リシェイプ）自前DB → RDS、Tomcat → Elastic Beanstalk
リファクタクラウドネイティブに再設計モノリス → マイクロサービス/サーバーレス

ディスカバリー

  • Application Discovery Service：エージェントレス（VMware vCenter経由、VM構成・利用率）、エージェント型（プロセス・ネットワーク接続の依存関係まで取得）。
  • Migration Evaluator：オンプレ利用実績からTCO・ライセンス最適化を含むビジネスケースを作成。
  • Migration Hub / AWS Transform：移行の計画・追跡（サービスの提供状況は変化しているため最新情報を確認）。
TASK 4.2

最適な移行アプローチの決定

サーバー・DB・データ量・期限から手段を選ぶ。

この章の考え方
移行の手段は、「何を・どれだけ・いつまでに・停止何分で」移すかで決まる。基本は「裏で複製し続け、最後に短時間で切り替える」。
場面で理解する

AWS MGN

場面
データセンターの契約満了まで6か月。400台を移す必要がある。
困りごと
手作業でサーバーを再構築していたら間に合わない。
解決
ブロックレベルの継続的な複製で、そのままEC2として起動する。
メリット
OSやアプリを変更せず、最終的な切り替えは数分〜数十分で済む。切り替え前に何度でもテスト起動できる。
注意
移行後の最適化（サイズ調整やモダナイズ）は別途行う。

DMS＋SCT

場面
Oracleのライセンス費が高いので、PostgreSQL（Aurora）に移りたい。
困りごと
業務を止めてデータを移す時間が取れない。
解決
SCTでスキーマを変換し、DMSのフルロード＋CDCで同期し続ける。
メリット
業務を止めずに移行でき、切り替え時の停止は数分で済む。
注意
ストアドプロシージャなど、自動変換できない部分は手直しが残る。

DataSync

場面
NASの200TBを移しつつ、移行期間中の更新にも追従したい。
困りごと
rsyncのような自前スクリプトは遅く、検証も手間がかかる。
解決
DataSyncのエージェントで、スケジュールに沿って差分を転送する。
メリット
高速で、暗号化・整合性の検証・帯域制限も標準で付いている。
注意
ファイル数が極端に多い場合は、タスクを分割する。

Storage Gateway（S3 File Gateway）

場面
工場のアプリはファイル共有に書き続けているが、ストレージは増設したくない。
困りごと
アプリを改修してS3のAPIに対応させる予算はない。
解決
オンプレミスにゲートウェイを置き、SMB/NFSで見せつつ、裏ではS3に保存する。
メリット
アプリはそのままで容量は無制限になり、よく使うファイルはローカルのキャッシュで速い。
注意
キャッシュに乗っていないファイルの初回アクセスは遅い。

Snowball Edge

場面
80TBを3週間で移したいが、回線は100Mbpsしかない。
困りごと
回線経由では半年近くかかる。
解決
物理的なデバイスにコピーして、AWSへ送る。
メリット
回線の帯域に関係なく、大容量を運べる。
注意
新規提供の状況が変化しているので、最新の情報を確認する。

Transfer Family

場面
取引先200社がSFTPでファイルを送ってくる。
困りごと
取引先に接続方法の変更を頼むのは現実的ではない。
解決
SFTPのエンドポイントをマネージドで用意し、保存先をS3にする。
メリット
取引先は何も変えずに済み、サーバーの運用も不要になる。
注意
既存のホスト名とSSH鍵を引き継ぐ準備をしておく。

TASK 4.3

移行後の新しいアーキテクチャ

「最小の変更で」マネージドへ乗せる。

この章の考え方
移行と同時に「運用しなくてよい部分」を増やすのが、クラウド移行の効果を大きくするコツ。ただし、コードの変更は最小限にとどめる。
場面で理解する

App2Container＋Fargate

場面
古いJavaアプリが30本ある。OSパッチの運用から解放されたい。
困りごと
作り直す予算も時間もない。
解決
既存のアプリをそのままコンテナ化し、Fargateで動かす。
メリット
コードを変えずにサーバー管理から解放され、デプロイも標準化できる。
注意
状態をローカルディスクに持つアプリは、先に外出しが必要。

Amazon MQ

場面
ActiveMQが前提のアプリ群がある。書き換える予算はない。
困りごと
SQSに移すには、メッセージングのコードを書き換える必要がある。
解決
マネージドなActiveMQ/RabbitMQであるAmazon MQに移す。
メリット
プロトコルはそのままで、ブローカーの運用だけをAWSに任せられる。
注意
大規模にスケールさせたいなら、将来はSQS/SNSへの移行を検討する。

RDS / Aurora

場面
DBAが、バックアップ・パッチ・冗長化の作業に追われている。
困りごと
DBの本来の改善に時間が割けない。
解決
マネージドのRDSやAuroraに移す。
メリット
バックアップ・パッチ・Multi-AZをAWSに任せられる。
注意
OSへのログインはできない。それが必要ならRDS Customにする。

RDS Custom

場面
パッケージ製品が、DBサーバーのOSへの管理者アクセスを要求する。
困りごと
通常のRDSではOSにアクセスできず、EC2で自前管理すると運用が重い。
解決
RDS Custom（Oracle / SQL Server）を使う。
メリット
OSへのアクセスとマネージドの自動化を両立できる。
注意
対応するエンジンとバージョンが限られる。
仕組みと要点
  • コンテナ化：App2Container で既存の.NET/Javaアプリをコード変更なしでコンテナ化 → ECS/EKS on Fargate。
  • メッセージング：ActiveMQ/RabbitMQ を使う既存アプリ → Amazon MQ（プロトコル互換、コード変更最小）。新規設計ならSQS/SNS。
  • Kafka → Amazon MSK。Hadoop/Spark → EMR。
  • DB：商用DB → RDS / Aurora、OS/DBへの特権アクセスが必要 → RDS Custom。キーバリュー → DynamoDB。
  • ファイル：Windows → FSx for Windows、NetApp → FSx for ONTAP。
TASK 4.4

モダナイゼーションと機能強化の機会

段階的にクラウドネイティブへ。

この章の考え方
一度に作り直すと失敗しやすい。動いているシステムを止めずに、小さく切り出して置き換えていくのがモダナイゼーションの定石。
場面で理解する

ストラングラーフィグパターン

場面
10年もののモノリスがある。一部の機能だけは頻繁に変更したい。
困りごと
全面的な作り直しは、何年もかかるうえに失敗のリスクが高い。
解決
その機能だけを新しいサービスとして切り出し、入口のルーティングで振り分ける。
メリット
いつでも中断でき、失敗しても元に戻せる。価値の高い部分から順に置き換えられる。
注意
切り出す単位はデータの持ち方で決める。DBの分離が最も難しい。

イベント駆動への移行

場面
夜間バッチで連携しているため、在庫の反映が翌日になる。
困りごと
バッチの処理時間が年々延び、業務時間に食い込み始めた。
解決
データの変更をイベントとしてEventBridgeやSNSで即座に伝える。
メリット
リアルタイムで連携でき、バッチの時間枠からも解放される。
注意
イベントの順序と重複を考慮した設計が必要。

目的別データベース

場面
1つのRDBで、全文検索・セッション管理・ランキングまで担っていて重い。
困りごと
RDBが苦手な処理まで押し込まれている。
解決
検索はOpenSearch、セッションはElastiCacheやDynamoDBに分ける。
メリット
それぞれが得意な処理を担当し、性能もコストも改善する。
注意
データの同期（二重書き込みを避け、CDCやイベントで連携）の設計が必要。
仕組みと要点
  • ストラングラーフィグパターン：API Gateway/ALBのルーティングで機能単位に新サービスへ切り替え、モノリスを徐々に置き換え。Migration Hub Refactor Spacesが支援。
  • イベント駆動化：EventBridge、SNS/SQS、Step Functions でオーケストレーション。
  • サーバーレス化：Lambda、Fargate、Aurora Serverless v2、DynamoDB。
  • 目的別データベース：キャッシュ（ElastiCache）、検索（OpenSearch）、グラフ（Neptune）、時系列（Timestream）。
SUPPLEMENT 1

コンテナとサーバーレス

近年の問題で比重が増している「モダンなコンピューティング」の選び方。

この章の考え方
サーバー（OS）の管理をどこまで自分でやるか、の違い。EC2 → コンテナ（EC2上） → Fargate → Lambdaの順に、管理の手間は減り、代わりに制約が増える。
場面で理解する

ECS と EKS の選び方

場面
コンテナを使い始めたい。
困りごと
Kubernetesは高機能だが、学習と運用の負荷が大きい。
解決
AWSだけで小さく始めるならECS、既にKubernetesの運用経験やツール資産があるならEKSを選ぶ。
メリット
チームのスキルに合った選択で、立ち上がりが速くなる。
注意
EKSはクラスターごとの料金と、バージョンアップの運用が発生する。

Fargate

場面
コンテナは使いたいが、ホストのパッチ当てやスケール管理はしたくない。
困りごと
EC2上のコンテナでは、ホストの運用が残る。
解決
タスク（ポッド）単位でコンピュートを確保するFargateを使う。
メリット
サーバー管理がなくなり、タスク単位で課金される。
注意
GPUや特殊なカーネル設定が必要な場合はEC2を使う。

Lambda

場面
画像がアップロードされたらサムネイルを作る。1日に数千回の短い処理。
困りごと
そのために常時サーバーを動かすのは無駄。
解決
イベントをトリガーにLambdaを実行する。
メリット
実行時間の分だけ課金され、スケールも自動になる。
注意
実行時間は最大15分。コールドスタートがあり、長時間や常時高負荷の処理には向かない。

EKS Pod Identity

場面
1つのEKSクラスターに多数のチームのサービスが同居している。
困りごと
ノードのロールに権限を付けると、全ポッドがその権限を持ってしまう。
解決
サービスアカウントごとにIAMロールを割り当てる。
メリット
ポッド単位で最小権限にでき、同居していても安全。
注意
ポッド側でEKS Pod Identity Agent（アドオン）が必要。
仕組みと要点

ECS と EKS

観点Amazon ECSAmazon EKS
向く場面AWSネイティブでシンプルに運用したいKubernetesの資産・ツール（Helm、マニフェスト）を活かしたい、マルチクラウド

  • キャパシティプロバイダー戦略：FARGATE に base を置き、残りを FARGATE_SPOT に weight で配分 → 中断耐性とコストの両立。

  • Lambda のコールドスタート対策：プロビジョニング済み同時実行（常時課金）、SnapStart（Java・Python・.NET、初期化済みスナップショットから起動）。
  • API Gateway：REST API（APIキー・使用量プラン・キャッシュ・WAF・リクエスト検証）、HTTP API（低コスト・低遅延・JWTオーソライザー）、WebSocket API（双方向・接続IDをDynamoDB等で管理し、@connections APIでサーバーからプッシュ）。エンドポイントタイプはエッジ最適化 / リージョン / プライベート。
  • EventBridge Pipes：ストリームやキュー（DynamoDB Streams、Kinesis、SQS等）→ フィルタ → エンリッチ → ターゲットをコードなしで1対1接続。
  • AppSync：GraphQL、リアルタイムサブスクリプション。
試験のツボ
  • 「Kubernetesのマニフェストとツールをそのまま使い、運用負荷を下げる」→ EKS（Fargate / Auto Mode / マネージド型ノードグループ）。
  • 「ポッドごとに異なるAWS権限」→ EKS Pod Identity（ノードのインスタンスロールに付けるのは誤り）。
  • 「サーバーからクライアントへリアルタイム通知」→ API Gateway WebSocket API または AppSync。
SUPPLEMENT 2

データ分析基盤

ストリーミング・データレイク・DWHの組み合わせ方。

この章の考え方
データ分析は「集める → ためる → 加工する → 分析する →見せる」の各段階でサービスが分かれる。まずS3（データレイク）にデータを集め、用途に応じて分析エンジンを選ぶのが基本の形。
場面で理解する

Kinesis Data Streams と Firehose

場面
クレジットカードの不正検知で、1件ずつ即座に判定したい／アクセスログをS3にためて後で分析したい。
困りごと
即時処理と蓄積では、求められる性質が違う。
解決
即時処理ならData Streams（自前のコンシューマーで処理）、ためるならFirehose（コード不要で配信）。
メリット
要件に合った遅延とコストになる。
注意
Firehoseはバッファリングするため、数十秒〜数分の遅延がある。

S3データレイク＋Athena

場面
月に数回だけ、分析担当者がSQLでデータを調べる。
困りごと
そのためにDWHを常時動かすのは高い。
解決
S3上のデータを、Athenaで直接クエリする。
メリット
サーバーが不要で、クエリした分だけの課金になる。
注意
Parquet化とパーティション分割をしないと、スキャン量が増えて高くつく。

Redshift

場面
毎朝、数百人がBIのダッシュボードで大量の集計を見る。
困りごと
Athenaでは、同時に大量のクエリを速く返すのが難しい。
解決
DWHのRedshiftにデータを入れ、BIから接続する。
メリット
大量の同時実行でも高速に集計できる。
注意
常時稼働のコストがかかる。変動が大きいならRedshift Serverlessにする。

Lake Formation

場面
部門ごとに見せてよいデータが違う。個人情報の列は、限られた人だけに見せたい。
困りごと
S3のバケットポリシーでは、ファイル単位でしか制御できない。
解決
Lake Formationで、テーブル・列・行の単位で権限を付ける。
メリット
1か所で細かい権限を管理でき、Athena・Redshift・EMRのどれにも同じ権限が効く。
注意
既存のIAMベースの権限から移行するときは、設定の整理が必要。

  • 「ストリームをS3にParquetで保存、管理不要」→ Firehose（Data Streams単体ではS3に書けない）。

場面

場面

困りごと
基盤モデルは社内の規程を知らない。社内文書で学習し直すのは高コスト。
解決
質問のたびに関連する文書を検索し、根拠としてモデルに渡す（RAG）。
メリット
学習は不要で、文書を更新しても同期するだけで反映され、回答に出典も付けられる。

メリット
どのモデルを使っても、同じルールで一律に制御できる。
注意

場面で理解する

AD Connector と Managed Microsoft AD

場面
既存のADのアカウントでWorkSpacesにログインしたい／AWS上のWindowsサーバー群をドメインに参加させたい。
困りごと
ADの情報をクラウドに置いてよいかどうかで、構成が変わる。
解決
ディレクトリをクラウドに持たないならAD Connector（プロキシ）。AWS上に本物のADが必要ならManaged Microsoft AD（オンプレミスのADと信頼関係を結ぶ）。
メリット
方針に合った形で既存のIDを活用できる。
注意
AD Connectorは、オンプレミスのADが落ちると認証できなくなる。

Gateway Load Balancer

場面
既存のPalo Altoなどのファイアウォールの運用ノウハウとルールを、AWSでも使いたい。
困りごと
アプライアンスを通信経路に入れると、スケールと冗長化が難しい。
解決
GWLBの背後にアプライアンスを並べ、GWLBエンドポイントを経路に挟む。
メリット
通信を改変せず透過的に検査でき、台数を増やしてスケールでき、故障したものは自動で切り離される。
注意
アプライアンスのライセンス費用は別にかかる。

Route 53 の位置情報ルーティング

場面
GDPRにより、EUの利用者のデータはEU内で処理しなければならない。
困りごと
レイテンシーベースでは、EUの利用者が米国に振り分けられる可能性がある。
解決
位置情報ルーティングで、EUからのアクセスは必ずEUのリージョンに向ける。
メリット
コンプライアンス要件を、DNSの段階で確実に満たせる。
注意
どの地域にも該当しないアクセス用のデフォルトレコードを必ず作る。

Outposts と Local Zones

場面
工場や病院のデータを施設の外に出せない／特定の都市で数ミリ秒の遅延が必要。
困りごと
リージョンは遠すぎるか、データの置き場所の要件を満たせない。
解決
施設の中に置くならOutposts、都市の近くでよいならLocal Zonesを使う。
メリット
AWSと同じAPIとツールのまま、低遅延やデータの所在地の要件を満たせる。
注意
Outpostsはハードウェアの設置・電源・ネットワークの準備が必要で、使えるサービスも限られる。
